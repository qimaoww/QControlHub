# 数据库迁移与更新健康检查

## 本次故障

2026-10-17 的现场数据库仍为 schema **73**。升级至 77 时需要执行
v75 的日志归属字段及覆盖索引迁移。现场有 11 个日志分区，多个分区为
数百 MiB；`pg_stat_statements` 记录单个日志索引构建耗时 **22.3 秒**，
另外两个索引分别耗时 14.5 秒、12.3 秒。控制面原先将连接、锁等待、
全部迁移及分区准备共用 **20 秒**，因此正常索引工作也会被取消。
后续启动还记录过等待迁移锁超时。

更新和回滚同时向 Compose 的 `up` 传入两个应用服务。
即使指定 `--no-deps`，Compose 仍会检查这两个服务之间的健康依赖。
控制面未及时就绪时，命令提前失败，前端停留在 `Created`。
现场旧版控制面随后恢复健康，但前端不会因此自动启动。
启动现有前端后，首页、`healthz`、`readyz` 均恢复成功。

## 修复

- `QCH_DATABASE_STARTUP_TIMEOUT` 默认 **5m**，允许 1s 至 1h。
  它覆盖迁移锁、迁移事务及启动准备；连接探测仍限时 20 秒。
- 内置 Compose、外部新安装及外部更新合并配置都传递此设置，
  控制面的健康检查启动宽限期同步采用此值。
- 安装器每阶段默认等待 **360 秒**，`-t SECONDS` 可覆盖。
  若将数据库启动时限调高，应同时提高 `-t`。
- 外部安装、更新和回滚先单独启动控制面，在容器内请求 `readyz`，
  确认成功后再启动前端。迁移期间输出明确的等待提示；超时后保留诊断。
- 启动日志记录预算、数据库后端 PID、迁移起止版本和提交耗时。
  取消后的迁移锁清理也有独立时限。

不改变 schema 版本、权限、密钥、网络、端口、数据库地址或业务数据。
历史迁移仍在事务内提交，取消时不会写入成功版本。
原有数据库版本高于回滚二进制支持范围时，仍会拒绝启动；应用镜像回滚
不等于数据库降级。升级前需保留数据库备份，不能删除卷或重建数据库
来处理健康检查失败。

## 验证

- 同一真实 PostgreSQL 锁等待场景：基线 `a980b78b23c3` 在 20 秒退出，
  错误为 `apply PostgreSQL schema: timeout: context deadline exceeded`。
  修复后的实际 `main` 子进程等待超过 22 秒，释放锁后正常提供 `readyz`。
- 设置 2s 启动时限：进程按时失败、迁移版本保持 73；释放锁后重试成功。
- 真实 Docker Compose 延迟启动：基线的联合 `up --no-deps` 报依赖不健康，
  前端为 `Created`；新的分阶段启动等待控制面后成功启动两个容器。
  此项仅验证容器编排，数据库迁移由上一项真实控制面测试覆盖。
- 回归外部更新、控制面就绪失败、回滚顺序、端点失败、拉取失败、
  原样保留 `.env`、自定义拓扑、密钥来源，以及跨部署环境变量隔离。
- 回归 v75/v76 的共享配置版本、流量账本、基础服务归属保留和并发迁移锁。
- `make non-browser-checks` 通过；完整 CI 结果见对应 PR。

自动化测试位于 `cmd/control-plane/startup_test.go` 和
`deploy/tests/quick-start-{update,compose}.sh`。新增启动测试会由现有
Debian、Alpine PostgreSQL CI 执行。
