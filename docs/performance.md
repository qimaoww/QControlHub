# 本地与远程 PostgreSQL 性能

本轮优化覆盖页面加载、配置/接入读取、任务轮询、日志/流量写入、状态巡检和历史查询。
内置 Compose PostgreSQL、本机独立 PostgreSQL 和外部远程 PostgreSQL 使用同一套优化路径，无需为了本地部署开启额外模式。
不改变 PostgreSQL 持久化模式，不要求 Redis，也不对任务状态、节点指标、权限或配置正文使用跨请求的长时间缓存。

## 已优化的路径

- 内核预设页只加载当前选中节点的配置；服务端先按节点筛选，再取出和解密正文，不再为每个节点读取整支节点队伍的配置。
- 客户端接入和 Sub-Store 使用同一条批量查询解析实际部署的配置版本及该版本的客户端附加密钥；不下载未部署配置，也不逐个查询历史版本。已删除配置和已清理的修订仍不会显示。
- 管理员节点列表把节点和可恢复安装命令状态两次读取合并发送。只有具备安装凭据管理权限的请求才走此路径；密文仍在控制面校验，不返回浏览器。
- 页面首次加载时，常用节点/任务读取与公共设置并行启动；一次渲染内复用相同读取。导航结束、切换页面和写操作均清空复用范围；独立取消信号、鉴权和后台轮询不复用旧结果。
- 配置编辑页的节点/配置/SS Rust 策略读取并行执行；工作区载入后的全局字段、端口字段和修订历史也并行加载。访问控制页的节点、配置和策略三组读取同时启动。
- 空任务队列只做一次轻量存在性查询，不再每两秒打开事务并锁住节点。存在任务时仍执行原有事务、运行中任务检查、能力检查和租约逻辑。
- 一批内核日志通过单条数组 INSERT 写入；去重记录、严重级别筛选和日志写入仍在一个事务内。
- 日志默认每个内核读取 1000 条，可选 100/200/500/1000/2000，四种内核最多 8000 条。前端保留全部结果供筛选，按每页 200 行显示；翻页、按内核或关键词筛选不再查询数据库。Agent 的 32 条仅是单个传输批次，不是保存总量。
- 端口流量上报一次锁定所有匹配策略，再用一条集合式 SQL 同时更新策略和每日增量，不再只把 2N 条语句塞入网络批次；本地也减少规划/执行开销和内存分配。保持计数器重启、周期切换、配额代次、重复采样和溢出保护，任一写入失败时整批回滚。
- 最新部署及客户端接入读取按节点/内核使用已有索引的 `LIMIT 1` 查找，不再扫描全部成功部署历史；历史上曾部署但当前不再声明能力的内核仍可查询。
- 监听端口发现的变更批量发送，减少持锁时的网络等待；流量写入与发现使用一致的策略加锁顺序。
- 在线状态和配额通知分别以单条原子语句领取变更。在线巡检跳过正被心跳锁定的节点，下次巡检重试；未发生变化的节点不加行锁。
- 总览对节点、配置、任务分别聚合一次；在线数量使用系统设置中的离线阈值，与节点列表保持一致。
- 任务和日志筛选按实际条件生成参数化查询，使重复执行时的查询计划仍能利用对应索引。补充节点/内核最近日志、任务状态/节点时间线、月度流量和历史清理索引。
- 月度流量改为一次窗口聚合，并保留跨配额重置代次累加和最新元数据语义。高压测试发现旧的两组聚合再关联路径存在 5 秒超时，修正后用同一负载复测。

批量传输基于项目已使用的 [pgx Batch](https://pkg.go.dev/github.com/jackc/pgx/v5#Conn.SendBatch)，没有新增运行时依赖。

## 本地数据库对比（不注入网络延迟）

本地专项以 PR 首个提交 `58f0ac9` 为基线，使用同一 PostgreSQL 17、回环 TCP、默认持久化设置和预热连接；基线和优化版顺序运行，不同时施压。
每项 100 次操作，重复 3 轮，下表为三轮耗时中位数。基线已经包含前面的批量网络发送等优化，因此这里是本地专项的进一步改善，不是与最早版本比较。

| 场景 | 本轮改动前 | 本轮改动后 | 改善 |
| --- | ---: | ---: | ---: |
| 16 端口流量上报 | 3.326ms | 2.046ms | 约 38% |
| 64 端口流量上报 | 9.314ms | 3.190ms | 约 66% |
| 256 端口流量上报 | 45.041ms | 10.384ms | 约 77% |
| 20 万条部署历史中取 800 个节点/内核最新记录 | 67.499ms | 5.397ms | 约 92% |

64 端口上报的 Go 分配从约 312KB / 3265 次降为 148KB / 691 次。SQL 执行计划回归以 `EXPLAIN (ANALYZE, BUFFERS)` 验证：20 万条部署历史只访问 800 条任务记录。组合查询先物化很小的最新版本投影，避免把配置关联下推到逐节点循环；测试中配置表和修订表各访问 200 行，而不是分别按 200 个节点重扫。流量语句预算同时检查：256 端口仍只有 BEGIN、基线读取、集合写入、COMMIT 四次调用，不是网络层隐藏着 512 条写入语句。

```bash
# 设置专用 QCH_TEST_DATABASE_URL；这里不注入延迟。
go test ./internal/store -run '^$' -bench 'BenchmarkLocalDatabase/traffic|BenchmarkLocalDeploymentHistory' -benchtime=100x -count=3
go test ./internal/store -run '^TestLocal' -count=1 -v
QCH_TEST_PRESSURE=1 go test ./internal/api -run '^TestLocalDatabasePressure$' -count=1 -v -timeout=5m
```

本地压力入口包含 64/128 并发，真实 HTTP 读取与持久化写入竞争同一个 20 连接池，使用与远程测试一致的数据集。压力结果受主机负载、存储和 CPU 影响；毫秒级基准的改善不等于所有页面会按同一比例加速。

本地最终版的 **128 并发、2 分钟无注入延迟持续测试**完成 61981 次操作，吞吐 514.8 次/秒，零错误。节点列表 P95 351ms；2000 条/内核日志 P95/P99 626/722ms；月度流量 P95/P99 797/899ms；最高单次流量请求 1.12s。此项测试单独运行，未同时启动其他基准或压力测试；测试会不断写入新日志，因此不能将不同持续时间的吞吐直接当作同条件速度对比。

```bash
QCH_TEST_PRESSURE=1 QCH_PRESSURE_DURATION=2m \
go test ./internal/api -run '^TestLocalDatabasePressure$/^workers128-delay0s$' -count=1 -v -timeout=5m
```

本地专项只复用已有索引，无新增 PostgreSQL 参数要求或额外 schema 迁移；远程场景也走相同集合式写入和有界查询路径。
本地追加优化后还重跑了 128 并发、20ms 转发延迟的 30 秒远程回归：11498 次操作、零错误，2000 条/内核日志 P95/P99 512/584ms。该次同时运行前端回归，仅作为兼容性压力验证，不与独立运行的本地基准作速度比较。

## 可复现的远程延迟对比

基准使用隔离 PostgreSQL 17 测试 schema、单个预热连接，在**每次数据库协议写入前注入 20ms 延迟**，包含事务消息和预处理协议消息。
这不是生产环境实测，也不是严格的固定 RTT 网络仿真；用来比较相同场景对远程往返的敏感程度。
基线为 `8b9ebf9`，每个场景测量 3 次，不含建库、准备数据和预热。以下远程对比及混合负载数字记录 PR 第一版 `58f0ac9`；本地专项继续在该版本上优化，单独列在上一节。

| 场景 | 改动前平均耗时 | 改动后平均耗时 | 协议写入次数/操作（前 → 后） |
| --- | ---: | ---: | ---: |
| 32 条日志入库 | 762.7ms | 106.7ms | 36 → 5 |
| 64 个端口流量上报 | 4111.3ms | 98.5ms | 194 → 4 |
| 空任务队列轮询 | 86.0ms | 20.7ms | 4 → 1 |
| 64 个节点状态变更 | 1412.2ms | 24.5ms | 67 → 1 |

复现命令（仅使用专用测试库）：

```bash
QCH_TEST_DATABASE_URL='postgresql://test_user:test_password@127.0.0.1:5432/qch_test?sslmode=disable' \
go test ./internal/store -run '^$' -bench BenchmarkRemoteDatabase -benchtime=3x -count=1
```

同一个 benchmark 文件可以在基线提交上运行。回归测试还检查固定 SQL/批量调用预算、批量写入错误回滚、并发通知去重、版本对应的密钥、单节点隔离和索引升级。

1000/2000 条日志也独立经过真实批量入库测试：在相同 20ms 协议写入延迟下，单节点串行写入分别为 3.48s/7.21s（约 287/278 条每秒）。这不是提高上报大小后的单个大包，而是所有日志按现有协议完整分批入库。命令：

```bash
go test ./internal/store -run '^$' -bench BenchmarkRemoteLogVolume -benchtime=1x -count=1
```

同样需设置 `QCH_TEST_DATABASE_URL`。浏览器测试实际载入 8000 条结果，仅维持 200 条日志 DOM；本机 Chromium 一次测得默认窗口载入 199ms、切换 2000 条/内核 312ms、翻页 49ms、跨全部结果筛选 19ms。浏览器网络数据由测试夹具提供，因此这些数值仅描述渲染和交互，不代替下面真实 HTTP+数据库压力结果。

## 高并发混合压力测试

`TestRemoteDatabasePressure` 使用真实 HTTP 服务和真实 PostgreSQL 数据，每个测试有独立 schema，结束自动清理。夹具为 200 个节点、3200 个端口、400000 条日志、50000 条任务、99200 条日流量记录、60000 条指标样本。

默认分三阶段，每阶段 30 秒：64 并发无额外延迟、64 并发注入 20ms 延迟、128 并发注入 20ms 延迟。半数 worker 持续请求节点、总览、任务、接入、配置、1000/2000 条日志、流量和指标；另一半持续写入日志/流量/指标并执行任务及在线巡检。请求间没有人为间隔，所有操作争用应用默认的 20 连接池；单操作超时为 5 秒。每类操作报告数量、错误数、P50/P95/P99/最大耗时，任一错误导致测试失败。

```bash
QCH_TEST_PRESSURE=1 QCH_PRESSURE_DURATION=30s \
go test ./internal/api -run '^TestRemoteDatabasePressure$' -count=1 -v -timeout=5m
```

必须同时设置专用 `QCH_TEST_DATABASE_URL`。`QCH_PRESSURE_DURATION` 可设为 `10s` 至 `2m`，每阶段 2 分钟时相应增大 Go 的 `-timeout`。模拟延迟通过只监听回环地址的 TCP 代理施加在应用到数据库的每次转发块上，不能等同于真实 WAN 的固定 RTT。

本机 PostgreSQL 17 / i5-12500 的一次修正后测试结果（共 44890 次操作，零错误）：

| 混合负载 | 总操作数 | 吞吐量 | 节点列表 P95 | 2000 条/内核日志 P95 / P99 | 月度流量 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 并发，无额外延迟 | 23480 | 774.8/s | 105ms | 271ms / 300ms | 491ms |
| 64 并发，20ms 转发延迟 | 10936 | 361.8/s | 201ms | 296ms / 387ms | 394ms |
| 128 并发，20ms 转发延迟 | 10474 | 345.1/s | 454ms | 546ms / 622ms | 627ms |

这些数字是有界夹具的实验结果，不是所有部署的容量承诺；日志内容长度、节点数量、保留天数、数据库资源和网络条件都会改变结果。测试进程结束阶段的 Go heap 也有记录，但不是峰值 RSS。

另外完成 128 并发 + 20ms 转发延迟的 **2 分钟持续测试**：42245 次操作、350.9 次/秒、零错误；2000 条/内核日志 P95/P99 为 542/648ms，月度流量 P95/P99 为 702/834ms，节点列表 P95 为 455ms，最长单次流量请求 1.18s。测试结束时 Go heap 为 23.1MiB，不能据此推断峰值内存或长期无泄漏。复现：

```bash
QCH_TEST_PRESSURE=1 QCH_PRESSURE_DURATION=2m \
go test ./internal/api -run '^TestRemoteDatabasePressure$/^workers128-delay20ms$' -count=1 -v -timeout=5m
```

## 连接池配置

`QCH_DATABASE_URL` 中 pgx 的连接池参数现在会被保留，不再被控制面固定值覆盖。支持 URI query 和 keyword DSN。默认值保持：

| 参数 | 默认值 |
| --- | --- |
| `pool_max_conns` | `20` |
| `pool_min_conns` | `2`（最大连接数为 1 时自动降为 1） |
| `pool_min_idle_conns` | `0` |
| `pool_max_conn_lifetime` | `30m` |
| `pool_max_conn_idle_time` | `5m` |
| `pool_health_check_period` | `30s` |

最小连接数和最小空闲连接数不得超过最大连接数，生命周期、空闲超时和健康检查周期必须大于零。
如果旧连接串填写了这些参数但以前实际未生效，升级前应重新核对它们。
例如可在现有连接串上添加 `&pool_max_conns=20&pool_min_conns=2&pool_min_idle_conns=2`；原有 `sslmode=verify-full`、证书和鉴权参数必须保留。

不要单纯调大连接数：它是每个控制面进程的上限，需要与 PostgreSQL `max_connections`、其他应用和数据库代理的限额共同核算。
先查看慢请求、数据库 CPU/磁盘、锁等待和连接数；数据库与控制面物理距离造成的延迟仍然存在，不能靠查询优化完全消除。

## 升级与回滚

schema 从 **40 升至 41**，新增六个索引。按项目现有启动迁移机制执行：在一个事务中取得迁移锁并应用 schema。
建索引会占用磁盘和 I/O，并可能等待或阻塞相关表写入；大表应安排维护窗口，升级前完成数据库备份，预留启动迁移时间。
本次不修改生产数据的业务含义，也不自动删除历史数据。

旧二进制会拒绝 schema 41。需要回滚到 schema 40 版本时，应同时恢复升级前的数据库备份和旧镜像；仅回滚应用镜像或手动降低迁移版本记录不是受支持的恢复方式。
