# 本地与远程 PostgreSQL 性能

本轮优化覆盖页面加载、配置/接入读取、任务轮询、日志/流量写入、状态巡检和历史查询。
内置 Compose PostgreSQL、本机独立 PostgreSQL 和外部远程 PostgreSQL 使用同一套优化路径，无需为了本地部署开启额外模式。
不改变 PostgreSQL 持久化模式，不要求 Redis，也不对任务状态、节点指标、权限或配置正文使用跨请求的长时间缓存。

## 已优化的路径

- 内核预设页只加载当前选中节点的配置；服务端先按节点筛选，再取出和解密正文，不再为每个节点读取整支节点队伍的配置。
- 客户端接入和 Sub-Store 使用同一条批量查询解析实际部署的配置版本及该版本的客户端附加密钥；不下载未部署配置，也不逐个查询历史版本。已删除配置和已清理的修订仍不会显示。
- 管理员节点列表把节点和可恢复安装命令状态两次读取合并发送。只有具备安装凭据管理权限的请求才走此路径；密文仍在控制面校验，不返回浏览器。
- 页面首次加载时，常用节点/任务读取与公共设置并行启动；一次渲染内复用相同读取。导航结束、切换页面和写操作均清空复用范围；独立取消信号、鉴权和后台轮询不复用旧结果。
- 配置编辑页的节点/配置/SS Rust 策略读取并行执行；工作区载入后的全局字段、端口字段和修订历史也并行加载。访问控制页的节点、配置和策略三组读取同时启动。
- 空任务队列只做一次轻量存在性查询，不再每两秒打开事务并锁住节点。存在任务时仍执行原有事务、运行中任务检查、能力检查和租约逻辑。
- 一批内核日志通过单条数组 INSERT 写入；去重记录、严重级别筛选和日志写入仍在一个事务内。
- 日志默认每个内核读取 1000 条，可选 100/200/500/1000/2000，四种内核最多 8000 条。前端保留全部结果供筛选，按每页 200 行显示；翻页、按内核或关键词筛选不再查询数据库。Agent 的 32 条仅是单个传输批次，不是保存总量。
- 内核日志列表按需 gzip 压缩响应体：单节点 2000 条/内核从 3.28 MB 降到 328 KB（约 10%），8000 条完整窗口从 2.5 MB 降到 60–330 KB。压缩在响应体达到 512 字节后才启用，小响应保持原有的 `Content-Length` 与分帧；已自带 `Content-Encoding` 的响应（如 Agent 二进制）和协议升级（Agent WebSocket）不参与压缩。
- 日志窗口查询改为只读覆盖索引 `core_logs_agent_engine_covering_idx`。`SELECT` 的每一列都随索引携带，为此前每行一次的回表随机读被彻底消除。在只有 2 GiB 内存、`shared_buffers` 128 MB、随机读延迟约 7 ms 的小型实例上，这正是"秒级以内返回"与"读取 2000 行需要约 14 s 随机 I/O"的区别。
- 该覆盖索引取代了旧的 `core_logs_agent_engine_recent_idx`（键相同，但不携带负载列）。schema v49 迁移会在创建覆盖索引后删除旧索引，避免同一查询路径维护两份索引。
- 同时删除 `core_logs_agent_recent_idx` 与 `core_logs_engine_recent_idx`。服务端的日志读取只有一条路径（`ListCoreLogs`：按选中内核 × 可选节点取最新窗口），覆盖索引能满足它的全部形状；这两个单列索引此前只被插入维护、没有任何查询使用。实测在该数据集上二者合计约 340 MB，删除后同一批查询仍全部走 `Index Only Scan`，而每条日志插入少维护两个索引。
- 内核日志写入路径因此只剩三个索引：主键、`UNIQUE (batch_id,entry_index)`（批次幂等去重标记）与覆盖索引。前者供清理时按批次定位，唯一索引供重复批次去重与级联删除，覆盖索引供读取；不再有只为写入付费的索引。

**存储体积的可配置杠杆（不需要重建表）。** 日志页的存储与 IO 成本几乎线性取决于保留窗口内的行数，而 `core_logs` 是纯追加表：缩短保留期会在数天内让旧行自然过期，新写入随之减少，无需 `ALTER TABLE`、无需停机，也不需要搬运历史数据。同一台实例上的实测换算（2.5M 行 / 1.5 GB、随机读 7.2 ms/页）可作为选择依据：

| 保留期 | 稳态行数（相同写入速率） | 覆盖索引与堆同步缩小 |
| --- | ---: | --- |
| 30 天 | 约 1070 万 | 约 6.4 GB |
| 7 天（默认） | 250 万 | 约 1.5 GB |
| 3 天 | 约 107 万 | 约 0.64 GB |
| 1 天 | 约 36 万 | 约 0.21 GB |

同一杠杆还有 Agent 侧：`core_log_minimum_level`（当前保存级别以下的日志不落库）与 `AgentCoreLogMaxMiB`／`AgentCoreLogRotateCount`（节点本地日志文件上限）。默认最低级别是 `debug`，即内核输出的每一行都入库；调试行在数量上通常占绝对多数，因此把最低级别提到 `info` 或 `warning` 往往比调整保留期减少更多行数，而且完全可逆：

```bash
# 读取当前值（设置页同样可改；改后控制面按新值筛选后续批次）
curl -fsS -H "Authorization: Bearer $QCH_ADMIN_TOKEN" \
  http://127.0.0.1:8080/api/v1/settings | grep -o '"core_log_minimum_level":"[^"]*"'
```

各级别允许取值 `debug|info|warning|error|critical|off`，保留期允许 `1|3|7|14|30` 天（`off` 表示停止保存新日志，历史仍按保留期清理）。

这些是运行时可调项而非 schema 变更，控制面启动时的清理任务会逐步收敛到新窗口，因此可以随时回退。

**关于按时间分区。** 分区表能进一步把清理从逐行 `DELETE` 变成 `DROP PARTITION`，并让热分区的索引常驻缓存。但 PostgreSQL 的分区是表的物理属性，普通表无法原地转成分区表，必须重建并搬运数据。在覆盖索引已经把读取路径的回表随机读清零之后，分区的剩余收益只有清理成本与缓存局部性，因此本版本不引入；当稳态行数达到千万级时再评估更合适。
- 流量累计表改为显式预留页内空间：`port_traffic_policies` 的 fillfactor 为 75，`port_traffic_daily_usage`、`port_traffic_daily_accounting`、`port_traffic_accounting_epochs` 为 85。这些表由代理上报高频改写同一批行（实测 25 条策略累计 2025 万次更新、约每秒一次），默认 fillfactor=100 会让每个新行版本落在页尾、页一满就分裂，死版本只是被标记可复用。某台实例上 25 行策略占了 2.4 MB，其中 94.6% 是空闲空间。预留空间让热更新以 heap-only tuple 留在页内，存储不再无界增长。已有表在后续清理与更新中逐步收敛，不要求重建。
- 端口流量上报一次锁定所有匹配策略，再用一条集合式 SQL 同时更新策略和每日增量，不再只把 2N 条语句塞入网络批次；本地也减少规划/执行开销和内存分配。保持计数器重启、周期切换、配额代次、重复采样和溢出保护，任一写入失败时整批回滚。
- 最新部署及客户端接入读取按节点/内核使用已有索引的 `LIMIT 1` 查找，不再扫描全部成功部署历史；历史上曾部署但当前不再声明能力的内核仍可查询。
- 监听端口发现的变更批量发送，减少持锁时的网络等待；流量写入与发现使用一致的策略加锁顺序。
- 在线状态和配额通知分别以单条原子语句领取变更。在线巡检跳过正被心跳锁定的节点，下次巡检重试；未发生变化的节点不加行锁。
- 总览对节点、配置、任务分别聚合一次；在线数量使用系统设置中的离线阈值，与节点列表保持一致。
- 任务和日志筛选按实际条件生成参数化查询，使重复执行时的查询计划仍能利用对应索引。补充节点/内核最近日志、任务状态/节点时间线、月度流量和历史清理索引。
- 月度流量改为一次窗口聚合，并保留跨配额重置代次累加和最新元数据语义。高压测试发现旧的两组聚合再关联路径存在 5 秒超时，修正后用同一负载复测。

批量传输基于项目已使用的 [pgx Batch](https://pkg.go.dev/github.com/jackc/pgx/v5#Conn.SendBatch)，没有新增运行时依赖。

## 本地数据库对比（不注入网络延迟）

本地专项以 PR 首个提交 `58f0ac9` 为基线，使用同一 PostgreSQL 17、回环 TCP、默认持久化设置和预热连接；基线和优化版顺序运行，不同时施压。
每项 100 次操作，重复 3 轮，下表为三轮耗时中位数。基线已经包含前面的批量网络发送等优化，因此这里是本地专项的进一步改善，不是与最早版本比较。

| 场景 | 本轮改动前 | 本轮改动后 | 改善 |
| --- | ---: | ---: | ---: |
| 16 端口流量上报 | 3.326ms | 2.046ms | 约 38% |
| 64 端口流量上报 | 9.314ms | 3.190ms | 约 66% |
| 256 端口流量上报 | 45.041ms | 10.384ms | 约 77% |
| 20 万条部署历史中取 800 个节点/内核最新记录 | 67.499ms | 5.397ms | 约 92% |

64 端口上报的 Go 分配从约 312KB / 3265 次降为 148KB / 691 次。SQL 执行计划回归以 `EXPLAIN (ANALYZE, BUFFERS)` 验证：20 万条部署历史只访问 800 条任务记录。组合查询先物化很小的最新版本投影，避免把配置关联下推到逐节点循环；测试中配置表和修订表各访问 200 行，而不是分别按 200 个节点重扫。流量语句预算同时检查：256 端口仍只有 BEGIN、基线读取、集合写入、COMMIT 四次调用，不是网络层隐藏着 512 条写入语句。

```bash
# 设置专用 QCH_TEST_DATABASE_URL；这里不注入延迟。
go test ./internal/store -run '^$' -bench 'BenchmarkLocalDatabase/traffic|BenchmarkLocalDeploymentHistory' -benchtime=100x -count=3
go test ./internal/store -run '^TestLocal' -count=1 -v
QCH_TEST_PRESSURE=1 go test ./internal/api -run '^TestLocalDatabasePressure$' -count=1 -v -timeout=5m
```

本地压力入口包含 64/128 并发，真实 HTTP 读取与持久化写入竞争同一个 20 连接池，使用与远程测试一致的数据集。压力结果受主机负载、存储和 CPU 影响；毫秒级基准的改善不等于所有页面会按同一比例加速。

本地最终版的 **128 并发、2 分钟无注入延迟持续测试**完成 61981 次操作，吞吐 514.8 次/秒，零错误。节点列表 P95 351ms；2000 条/内核日志 P95/P99 626/722ms；月度流量 P95/P99 797/899ms；最高单次流量请求 1.12s。此项测试单独运行，未同时启动其他基准或压力测试；测试会不断写入新日志，因此不能将不同持续时间的吞吐直接当作同条件速度对比。

```bash
QCH_TEST_PRESSURE=1 QCH_PRESSURE_DURATION=2m \
go test ./internal/api -run '^TestLocalDatabasePressure$/^workers128-delay0s$' -count=1 -v -timeout=5m
```

本地专项只复用已有索引，无新增 PostgreSQL 参数要求或额外 schema 迁移；远程场景也走相同集合式写入和有界查询路径。
本地追加优化后还重跑了 128 并发、20ms 转发延迟的 30 秒远程回归：11498 次操作、零错误，2000 条/内核日志 P95/P99 512/584ms。该次同时运行前端回归，仅作为兼容性压力验证，不与独立运行的本地基准作速度比较。

这不是生产环境实测，也不是严格的固定 RTT 网络仿真；用来比较相同场景对远程往返的敏感程度。

## 高并发混合压力测试

`TestRemoteDatabasePressure` 使用真实 HTTP 服务和真实 PostgreSQL 数据，每个测试有独立 schema，结束自动清理。夹具为 200 个节点、3200 个端口、400000 条日志、50000 条任务、99200 条日流量记录、60000 条指标样本。

默认分三阶段，每阶段 30 秒：64 并发无额外延迟、64 并发注入 20ms 延迟、128 并发注入 20ms 延迟。半数 worker 持续请求节点、总览、任务、接入、配置、1000/2000 条日志、流量和指标；另一半持续写入日志/流量/指标并执行任务及在线巡检。请求间没有人为间隔，所有操作争用应用默认的 20 连接池；单操作超时为 5 秒。每类操作报告数量、错误数、P50/P95/P99/最大耗时，任一错误导致测试失败。

```bash
QCH_TEST_PRESSURE=1 QCH_PRESSURE_DURATION=30s \
go test ./internal/api -run '^TestRemoteDatabasePressure$' -count=1 -v -timeout=5m
```

必须同时设置专用 `QCH_TEST_DATABASE_URL`。`QCH_PRESSURE_DURATION` 可设为 `10s` 至 `2m`，每阶段 2 分钟时相应增大 Go 的 `-timeout`。模拟延迟通过只监听回环地址的 TCP 代理施加在应用到数据库的每次转发块上，不能等同于真实 WAN 的固定 RTT。

本机 PostgreSQL 17 / i5-12500 的一次修正后测试结果（共 44890 次操作，零错误）：

| 混合负载 | 总操作数 | 吞吐量 | 节点列表 P95 | 2000 条/内核日志 P95 / P99 | 月度流量 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 并发，无额外延迟 | 23480 | 774.8/s | 105ms | 271ms / 300ms | 491ms |
| 64 并发，20ms 转发延迟 | 10936 | 361.8/s | 201ms | 296ms / 387ms | 394ms |
| 128 并发，20ms 转发延迟 | 10474 | 345.1/s | 454ms | 546ms / 622ms | 627ms |

这些数字是有界夹具的实验结果，不是所有部署的容量承诺；日志内容长度、节点数量、保留天数、数据库资源和网络条件都会改变结果。测试进程结束阶段的 Go heap 也有记录，但不是峰值 RSS。

另外完成 128 并发 + 20ms 转发延迟的 **2 分钟持续测试**：42245 次操作、350.9 次/秒、零错误；2000 条/内核日志 P95/P99 为 542/648ms，月度流量 P95/P99 为 702/834ms，节点列表 P95 为 455ms，最长单次流量请求 1.18s。测试结束时 Go heap 为 23.1MiB，不能据此推断峰值内存或长期无泄漏。复现：

## 按节点日志首屏与分页（后续修正）

按节点查看日志不再用 `Promise.all` 等待整份节点列表。日志先独立显示，节点名称和采集状态随后更新；短时间切换节点可复用最近 10 秒内成功读取的节点元数据，正常轮询仍会重新校验。节点元数据失败不会丢弃日志，也不会把旧在线状态当作当前采集健康状态。

首次选择未缓存节点且每内核上限大于 200 时，先请求每内核最新 200 条；若有内核达到这一数量，再重新读取完整的 1000／2000 条窗口并替换预览。所有内核都不足 200 条时，首批已是完整结果，无须第二次查询。这缩短了首批内容的数据库读取、传输和渲染路径，但繁忙节点的冷加载会多一次小查询，不意味着总网络流量减少。普通后台刷新不会退回小预览。

完整结果只在当前登录会话的内存中保留：最多 3 个节点/上限组合、30 秒有效期、约 16MiB 的文本和对象开销估算预算，超出预算的窗口不缓存。这不是进程峰值内存上限；活动窗口仍完整保留。回访先显示缓存并标注“正在更新”，后台重新校验；退出登录、权限拒绝和过期不会复用旧结果。快速切换会取消旧请求并丢弃迟到响应。后台补齐失败时明确标注“当前仅显示部分日志”，不会将预览缓存为完整窗口。

分页放在表格外的右上工具栏和底部，不再插入表头与日志行之间。DOM 仍为每页 200 行，关键词和级别/内核筛选仍作用于全部已加载结果，不发起额外数据库读取。预览阶段会标明正在补齐，此时计数与搜索仅覆盖已加载内容。

回归入口：

```bash
node frontend/core_logs_smoke.mjs
QCH_BROWSER_SMOKE_MODE=logs node frontend/agents_browser_smoke.mjs
```

测试覆盖慢节点列表、首批/完整响应分别阻塞、缓存回访、快速切换、请求取消、权限拒绝、退出后的迟到响应、元数据/补齐失败、LRU/有效期/内存预算，以及 8000 条结果的搜索和桌面/手机分页布局。本机 Chromium 夹具一次测得切换反馈 7ms、首批响应后的渲染 39ms、缓存回访 10ms；这些数字不含真实 WAN 等待，不能当作线上延迟承诺。

混合压力入口额外包含 `agent_id=...&limit=200` 和 `agent_id=...&limit=2000`，分别模拟按节点首批和完整窗口读取。使用上面的专用测试库环境变量运行：


本次实测两轮均为 128 并发、每轮 2 分钟：远程 20ms 转发延迟完成 45319 次操作、零错误，按节点 200/2000 条读取 P95 分别为 406/430ms；本地完成 67860 次操作、零错误，对应 P95 为 338/365ms。合计 113179 次操作。连接池竞争下首批请求仍有数百毫秒等待，不能将缓存切换的前端耗时等同于数据库请求耗时；测试请求组合也已增加两个节点日志路径，不与前一轮总吞吐作严格速度对比。

本次后续修正不改变数据库 schema、API 参数、日志保留期或上报批次大小；回滚只需恢复前一版前端。

## 低内存实例上的日志窗口取数（schema v49）

一台 2 vCPU / 1.9 GiB 内存的实际部署上，内核日志页在切换单节点时长时间停留在“正在加载日志”，反向代理记录到
`upstream timed out (110: Connection timed out) while reading response header from upstream`
（读后端响应头超时），后端进程日志对应 `HTTP request failed error="context canceled"`。

在同一实例上直接测量，排除了数据库查询本身、表/索引膨胀和容器限流：

| 观测项 | 实测值 |
| --- | ---: |
| `core_logs` 行数 / 堆大小 / 索引大小 | 250 万行 / 713 MB / 850 MB |
| `shared_buffers` / 主机内存 | 128 MB / 1.9 GiB（swap 已使用 267 MB） |
| 4 KB 随机读延迟 | 约 7.2 ms（顺序读约 1.6 GB/s） |
| 索引叶密度 / 碎片率 | 62% / 70% |
| 死元组占比 | 0.0%（存活元组 91.9%） |
| 容器 CPU / 内存限制 | 无限制 |

数据库查询本身只要数十毫秒，但被卡住的请求在数据库里持续处于 `active` + `IO/DataFileRead` 状态数十秒。
原因是窗口查询为每个被选中的行回表一次，`Heap Fetches: 2000`；在 128 MB 共享缓冲区和 2 GB 内存下，
最近的日志行大多不在缓存中，于是每次回表都是一次随机页读。按 7.2 ms/页计算，2000 行即约 14 秒纯 I/O 等待，
叠加客户端重试与取消就表现为“加载很久很久”。

同一份生产规模数据（200 万行、20 节点、四内核）上的对照实验：

| 查询 | 现有索引（回表） | 覆盖索引（仅索引） |
| --- | --- | --- |
| 单节点 · 全内核 · 1000 条/内核 | `Index Scan`，`Heap Fetches` > 0 | `Index Only Scan`，`Heap Fetches: 0` |
| 单节点 · 全内核 · 2000 条/内核 | `read=163` 块 | `read=105` 块 |
| 覆盖索引大小 | — | 415 MB（该数据集） |

因此本轮把窗口查询改为只读覆盖索引，并在 schema v49 中删除被取代的旧索引。传输侧同时启用 gzip：
同一次测量中单节点 2000 条/内核的响应体由 3.28 MB 降为 328 KB。

这两项都不改变 API 参数、日志保留期、上报批次或前端交互语义；navigate 到日志页仍是同样的 1000／2000 条窗口，
只是取数与传输代价大幅下降。回滚需要同时部署前一版二进制（旧索引会在下次以旧版本启动时由 `schemaSQL` 重建）。

## Agent 心跳与指标写入（schema v50）

日志窗口修好之后，同一台实例的 CPU 仍然长期在 13% 左右（2 vCPU），`iowait` 不高但写入次数极大。
逐项实测后定位到真正的原因不是日志，而是 **Agent 行的写放大**：

| 观测项 | 实测值 |
| --- | --- |
| `agents` 行数 / 表大小 | 17 行 / 152 页（每行约 8 KB，被 `metrics` 快照撑开） |
| `agents` 更新速率（45 秒采样） | 12.8 次/秒 |
| `agents` HOT 命中率 | **0.0%**（585 次更新中 0 次堆内更新） |
| 数据库累计元组更新（8 天） | 6749 万次 |
| 磁盘实际写入（进程级） | 约 277 KB/s，全部来自 PostgreSQL |

原因是 `agent_metrics_interval_seconds` 默认为 1，每个节点每秒推送一次指标，而这份约 1.2 KB 的
`metrics` JSONB 与身份、能力、路由字段同处一行。每次推送都要重写整行，并且因为 `UPDATE` 触及了
`agents_active_seen_idx`（建在 `last_seen` 上），**任何一次心跳都不可能成为堆内更新**：它必须同时
向 4 个索引写入新条目。死元组随之以每秒约 296 个的速度产生，autovacuum 只能不停地清扫这张 17 行的表。

在本地 PostgreSQL 上做的对照实验（17 行、每行约 1.2 KB 快照、20 秒 4 并发）：

| 方案 | HOT 命中 | 20 秒死元组 | 稳态 WAL/次写入 |
| --- | ---: | ---: | ---: |
| 现状：宽行 + 4 索引 + 默认 fillfactor | 0.0% | 5932 | 975 B |
| 拆分：快照入侧表 + `fillfactor=70` | **100%** | **146** | 823 B |
| 仅瘦身（保留 2 语句侧表写入） | 100% | 299 | 770 B |

v50 因此做了三件事：

1. Agent 上报的指标快照移入 `agent_live_state`（两列 + 主键，`fillfactor=70`），每次推送只重写一行窄元组；
2. `agents` 设置 `fillfactor=70`，让心跳本身也能留在页内，并把控制面观测到的 `observed_public_ip`
   从 JSONB 提为独立列——它由 WSS 会话写入，与 Agent 自己的快照更新时机不同，放在快照里会被下一次推送覆盖；
3. 删除 `agents_active_seen_idx`。它建在每次心跳都会变化的 `last_seen` 上，是"心跳永远无法堆内更新"的
   直接原因；面板对它的唯一用途是在一张每节点一行的表上做在线计数，顺序扫描同样快且不必为每次心跳
   永久维护一个 btree 条目。

迁移是元数据操作：把旧列改名后 `DROP`，列与其外置存储一起释放，不逐行重写，因此快照再大也不会让升级变慢；
已有快照会先复制进侧表，`observed_public_ip` 也会在旧列被丢弃前单独取出。升级后首次推送前，面板仍能读到
迁移过来的公网地址与探测结果。

回滚需要同时部署前一版二进制：旧版会在启动迁移时按 `schemaSQL` 重建 `metrics` 列与
`agents_active_seen_idx`，但**拆分期间写入 `agent_live_state` 的快照不会被搬回**，回滚后需要等节点
重新推送一次指标才会恢复。

## 连接池配置

`QCH_DATABASE_URL` 中 pgx 的连接池参数现在会被保留，不再被控制面固定值覆盖。支持 URI query 和 keyword DSN。默认值保持：

| 参数 | 默认值 |
| --- | --- |
| `pool_max_conns` | `20` |
| `pool_min_conns` | `2`（最大连接数为 1 时自动降为 1） |
| `pool_min_idle_conns` | `0` |
| `pool_max_conn_lifetime` | `30m` |
| `pool_max_conn_idle_time` | `5m` |
| `pool_health_check_period` | `30s` |

最小连接数和最小空闲连接数不得超过最大连接数，生命周期、空闲超时和健康检查周期必须大于零。
如果旧连接串填写了这些参数但以前实际未生效，升级前应重新核对它们。
例如可在现有连接串上添加 `&pool_max_conns=20&pool_min_conns=2&pool_min_idle_conns=2`；原有 `sslmode=verify-full`、证书和鉴权参数必须保留。

不要单纯调大连接数：它是每个控制面进程的上限，需要与 PostgreSQL `max_connections`、其他应用和数据库代理的限额共同核算。
先查看慢请求、数据库 CPU/磁盘、锁等待和连接数；数据库与控制面物理距离造成的延迟仍然存在，不能靠查询优化完全消除。

## 升级与回滚

schema 从 **40 升至 41**，新增六个索引。按项目现有启动迁移机制执行：在一个事务中取得迁移锁并应用 schema。
建索引会占用磁盘和 I/O，并可能等待或阻塞相关表写入；大表应安排维护窗口，升级前完成数据库备份，预留启动迁移时间。
本次不修改生产数据的业务含义，也不自动删除历史数据。

旧二进制会拒绝 schema 41。需要回滚到 schema 40 版本时，应同时恢复升级前的数据库备份和旧镜像；仅回滚应用镜像或手动降低迁移版本记录不是受支持的恢复方式。
