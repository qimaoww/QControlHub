# 现有页面多用户适配验收

## 基准与环境

- 基准：`8834b33d2fad0539f935b14976e2892ddbd38a71`，从最新 `origin/main` 创建 `codex/multi-user-page-adaptation`；交付前再次 fetch 确认 main 未变化。
- 使用真实 PostgreSQL 17、密码登录、cookie、CSRF 和页面模块。浏览器为 Chromium，桌面 `1440×1000`、手机 `390×844`、平板 `820×1180`。
- 页面审计：管理员、普通用户 A、普通用户 B、无权限且无资源账号，19 个路由/已有入口，三个视口，共 **228 次**。最终结果：零脚本异常、零横向溢出；拒绝访问按现有规则记录。
- 额外账号：仅 `tasks.read`、仅 `traffic.read`，均有自有节点；验证页面不会额外要求 `agents.read` 或 `settings.read`。
- A、B 各有自有节点，管理员的同一节点/同一 Mihomo 内核分别分享给 A、B，端口及实例独立。自动回归另覆盖待接受、接受、停用、撤销及无资源状态。
- 截图环境的心跳、配置部署结果由隔离夹具写入，任务结果明确标记未执行内核。截图用于证明真实页面/API 的归属及展示，不代表客户端网络已连通。四内核真实 systemd 多实例日志测试单独执行并保存结果。

## 发现的问题与修复

| 问题 | 根因 | 修复及回归 |
| --- | --- | --- |
| 前端仍接受 operator/auditor/readonly 并按历史角色授予权限；管理员快捷返回绕过传入资源限制 | 前端模型落后于服务端 admin/user＋显式权限 | 只接受当前两种角色，保留 operator 作为既有 UI capability 别名；资源限制先于 admin 快捷判断。历史环境令牌仍由后端转换成 user＋显式权限。同步更新旧浏览器夹具 |
| 有 tasks.read 却打不开任务页 | 固定请求 `/agents`、`/settings`，其中任一 403 拒绝整页 | 按显式读取权限请求辅助数据；窄权限下以本人任务的节点 ID 建立筛选项 |
| 有 traffic.read 却打不开流量页 | 固定依赖 `/agents` | `/traffic-policies?view=page` 仅返回已授权流量范围所需节点 ID、名称、在线状态、管理标志、内核和流量 feature；原数组响应兼容保留；写操作继续检查具体节点归属 |
| 普通用户的 HTTP-01 自有节点不出现在授权选择中 | 用 `/agents` 的读取权限代替证书节点授权，失败后吞为 [] | 复用 `/certificate-http-nodes` 的 owned/domains 范围，取消多余 fleet 请求；真实浏览器验证只有任务或流量读权限也可选本人节点 |
| 证书晚到响应可能覆盖新弹窗，初次读取取消后仍可能建立轮询 | 缺少页面/弹窗请求序号；abort 清理在 await 初次读取之后才注册 | 读取序号、账号数据及路由联合校验；先注册清理；注销显式 dispose；清理凭据表单、筛选和计时器。浏览器延迟真实响应再切换路由验证 |
| 证书授权撤销后旧详情仍保留；Escape 关闭后延迟请求可能重开表单 | 永久的 403/404 被当作临时错误；原生 close 事件未失效请求序号 | 失权关闭详情并刷新列表；所有关闭路径失效请求。真实所有者撤销、Escape＋真实 HTTP 延迟在桌面/手机回归及录屏通过，见 [审查记录](review.md) |
| 同浏览器其他页切换账号后，旧 A 页面可能显示 B 数据 | cookie 已变，页面内 session/偏好仍为 A；GET 未绑定页面会话 | 所有已登录页面请求附现有 CSRF 会话标识；GET/HEAD 若与 cookie 会话不匹配返回 401，清空旧页面，不撤销新 B 会话；无此头的既有 API 客户端保持兼容 |
| 空闲编辑器不感知分享修改、停用或权限变化 | 依赖特定页面的操作/轮询，没有统一空闲校验 | 复用 createPoller，每 10 秒及回到前台/聚焦校验会话和本人授权；授权身份变化清掉旧资源缓存并重读。使用量计数变化不打断编辑；延迟响应不能更新新账号 |
| 缺失安装/实例信息被显示为未安装或尚未配置；离线实例先被当作未配置 | false 与未知混用；状态判断优先级错误；自有节点轮询跳过缺失 runtime 的内核 | 自有/共享节点均区分 installed 的 boolean 与未知，补齐缺失 runtime 的轮询更新；另检查实例是否存在、config_uncertain、节点在线、运行状态、执行任务及失败原因；配置选择只显示保存/部署信息 |
| 一个自有节点加一个共享节点也显示宿主批量入口，但无法进入批量操作 | 入口按可见总数判断，实际批量功能按可管理节点数判断 | 入口使用既有具体节点授权，至少两个可管理节点才出现；A/B 的真实浏览器回归通过，桌面/手机同账号前后截图与录屏已保存 |
| 顶部在线数与刚读取的节点列表不一致；无读取状态却显示等待连接 | 页面用了新快照，顶部仍用缓存汇总；未知默认为零 | 对节点、流量、IP 质量、TCP、日志页面以当前授权节点快照计算；没有可用状态时显示“节点状态未知” |
| 无配置读取权限被展示为没有可配置节点 | 没有 agents.read 时空数组进入无资源分支 | 使用已有错误样式明确“当前账号无权查看配置”，隐藏入口及 API 授权保持一致 |

## 权限、任务及状态的一致性

- 页面 capability 检查不产生服务端权限。`requirePermission/requireAllPermissions`、ConfigScope、PrincipalAuth 和具体节点/配置/实例 Store 校验继续决定资源范围。
- 新流量元数据接口使用同一 Principal 范围，不能通过 `owner_id`、`agent_id` 查询字段选中 B；也不返回 runtime、metrics、labels、owner 或配置内容。已有接口默认仍返回数组。
- 同节点同内核，A/B 的工作区、配置 ID/版本、任务、共享实例和日志 source 分别关联本人；更换 ID、任务取消/重试、过期版本及重复提交均有回归。
- 任务领取、续租、完成、撤销及证书授权保留现有服务端二次检查。撤销 A 不影响 B 已排队任务；停用 A 不会注销 B。
- 普通用户自有节点的 `can_manage=true` 与共享接收者的 `can_manage=false` 区分；宿主升级、卸载、TCP/IP 检测不会因有全局执行权限而对共享接收者开放。
- 配置草稿/保存版、已部署版和运行状态独立；新增、保存、校验、部署、启停、修改、删除由现有配置与实例链路处理。未知和离线不等于停止，任务失败不覆盖仍在运行的实例。
- 浏览器账号偏好仍使用现有 accountStorage；配置凭据草稿仍只驻留账号内存。新校验复用现有传输、轮询、AbortSignal 和路由刷新机制，未新增存储系统。
